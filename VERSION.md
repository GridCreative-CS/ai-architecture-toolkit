# Version

AI Architecture Toolkit — **v4.6.0**

Projects adopting the toolkit should record this version in their project `CLAUDE.md`. Breaking workflow changes (renumbered steps, renamed output paths, changed handoff contracts) are marked **BREAKING** below, with the migration action a project must take.

## Changelog

### v4.6.0 — 2026-08-18

Requirement-traceability release. Step 6a reviews were finding real defects across three rounds instead of one: in the reference project's P12, the round-2 and round-3 findings were largely present in the original implementation — missed, not introduced — and the review only became complete once someone wrote a criterion-by-criterion §11b audit by hand. The cause was structural: a broad quality checklist with no required link from each acceptance criterion to its implementation, its negative/edge test, and its evidence. This release makes the review systematic rather than checklist-based. Each Step 6a review is heavier; the return is fewer rounds per Part and PASS claims that mean something.

- **BREAKING — the Part Quality Report gains required sections.** `ai/templates/code-quality-checklist-template.md` adds a **Review snapshot** block (base commit, diff command, uncommitted worktree files, generated/untracked Part files), **§3b Requirement coverage matrix**, and **§10b Remediation log**; §12's DONE gate now depends on them. Sections 1–12 keep their numbers (§7 contract surfaces is unmoved) — the new sections use the toolkit's letter-suffix convention. Migration: re-sync the toolkit copy before the next Part and apply from the next Part onward; do not retro-fit completed Parts. Reports produced under v4.5.x remain valid for Parts already reviewed.
- **New: criterion IDs in the feature spec.** `ai/templates/feature-spec-template.md` requires stable, **append-only** IDs — `DR-nn` (§6), `SEC-nn` (§9), `AC-nn` (§11), `UIAC-nn` (§11b). They key the coverage matrix and the coverage map. `feature-spec-generator` emits them; both reconcilers must never renumber (rewording keeps the ID; a dropped criterion stays marked `WITHDRAWN — <reason>`); `ui-compliance-check` findings now cite the `UIAC-nn` they relate to. Migration: specs written before this release keep working — matrix rows fall back to the section plus the verbatim criterion text, and IDs are assigned at the spec's next reconciliation. `compliance-report-template` changes its violation-identifier example from `AC-001` to `CV-001` to free the `AC-` namespace (comment-only; the example report follows).
- **§3b requirement coverage matrix — the whole slice, in every Part's report.** Columns: requirement, source, implementation location, positive test, negative/edge test, verification evidence, status. Status vocabulary: `COVERED-THIS-PART` / `COVERED-EARLIER (Pxx)` / `NOT-YET (owner Pxx)` / `DEFERRED (<step>, owner Pxx)` / `N/A — <reason>`. Non-owned rows are one-liners, so the sweep costs little; covering only the Part's own criteria would relocate the hole this closes. A criterion at `NOT-YET` whose owning Part is already `DONE` surfaces at the next Part's review instead of at Step 6b. The slice's final Part must show zero `NOT-YET`.
- **`ai/prompts/code-quality-reviewer.md`: ten checks → twelve.** Check 11 is the **dimension audit** — a nine-row sweep (D1 role/authorization behavior including absence of denied-role requests, D2 per-source loading/success/empty/error states, D3 async lifecycle incl. supersession, clear/reset and unmount, D4 error mapping and trace-reference preservation, D5 localized display of domain values, D6 accessibility and design system, D7 observable cache invalidation, D8 server-derived vs client-calculated values, D9 shared-component and public-contract changes), each `PASS` / `FAIL` / `DEFERRED (owner)` / `N/A — reason` with evidence. Check 12 is the **requirement coverage audit** of §3b. Also new: a **Review snapshot** section that freezes the reviewed target and restarts the review if production files change mid-review; **evidence rules for claims** (catalogue parity, a call's presence, and implementation inspection are not evidence); and a **re-review closure protocol** — re-run every previous finding's test, verify no assertion was weakened, review the remediation diff separately, check every branch it touches, confirm §3b was updated.
- **Dimension applicability is mechanical.** `plan-decomposer` v2.4.0 makes its existing Backend/Frontend/Shared-Contract/Infrastructure classification explicit via the new optional PART_SPEC field `part_type` (plus `criteria_covered`, and a Type column in the Parts Index). When `part_type` is absent, the reviewer classifies from `file_touch_points` and records the classification it used, so `N/A` rows stay auditable.
- **New required OVERVIEW section: `## Requirement Coverage Map`** (`plan-decomposer` v2.4.0) — every feature spec criterion, its owning Part, and where it is verified. A criterion no Part owns is a decomposition defect that blocks Step 5 completion. **Also a handoff-contract change:** an executor running under v4.6.0 expects an OVERVIEW section that pre-v4.6 files lack. Migration: for slices decomposed before this release, the executor derives the map once from the feature spec at its next Part and writes it into the existing `OVERVIEW.md` — no re-decomposition, and completed Parts are not revisited. The skill's file paths are now written out in full (`./ai-parts/<slice-id>/…`); the previous `./ai-parts/` shorthand convention is removed, since abbreviated paths were being reproduced literally.
- **`ai/guides/code-quality-standard.md` §10 extended in place** (no renumbering): **structural vs behavioral tests** — "the component / query / key / guard exists" is not a test; it must fail when the implementation is removed, with a table of the recurring offenders (role restrictions, display mapping, cancellation, cache refresh, gating, error mapping) — plus a **mutation check protocol**, mandatory when a Part implements an **authorization guard, cache invalidation/refetch, cancellation/supersession, or error→message mapping**: break it, observe the failure, restore, re-run green, record the file and line, the mutation, and the observed failure; never commit the mutation. Plus a claims-require-evidence rule.
- `part-executor-tdd` v1.4.0: records the review snapshot at Part start; builds the §3b baseline from the spec plus the coverage map **before** implementing (so the negative and edge cases are known up front); runs the mutation checks; new quality gates for §3b completeness, mutation evidence, and the snapshot; new **remediation protocol** after a rejection (fix within the Part under TDD, never weaken an assertion, re-run every prior finding's test, write §10b, record a new snapshot).
- Engineering workflow: Step 5 requires the coverage map with no unowned criterion; Step 6 requires the snapshot, §3b, and mutation checks; Step 6a freezes the snapshot, runs twelve checks, and adds the re-review protocol; **Step 6b gains a requirement coverage rollup** (zero `NOT-YET`, every `DEFERRED (Step 6b)` verified) — mirrored in `ai/templates/slice-verification-checklist-template.md`. `slice-preparation-runner` reports coverage in its completion summary. Step numbering unchanged (0b–8).
- Agents: `code-reviewer-agent` (twelve checks, sweep-don't-sample, frozen target, remediation stance, new forbidden actions); `qa-agent` (structural-vs-behavioral, mutation triggers, a negative case per criterion); `frontend-agent` (new methodology sections for per-source states, async lifecycle, display values, invalidation); `backend-agent` (authorization proven from both sides, trace-reference survival, server-owned values, invalidation, mutation checks).
- New examples: `ai/examples/example-part-quality-report.md` (filled §3b with all five status values, recorded mutation checks, snapshot block) and `ai/examples/example-part-review.md` (dimension audit with a `FAIL` and a justified `N/A`, coverage audit catching a `COVERED` claim resting on a test that passes with the implementation removed).
- **Working rule 1 now states the gate condition.** `architecture/architecture-final.md` and `architecture/adr/*.md` are authoritative once they exist as real project outputs **and** `architecture/architecture-final-gate.md` records verdict `APPROVED` or `APPROVED WITH NOTES`; until then the final architecture is a draft that must not drive ADR generation, delivery planning, feature specs, compliance checks, decomposition, or implementation. The gate and the reconcilers still read the ungated document — the restriction is on downstream consumption only. v4.5.0 added the gate to rule 2 and left rule 1 unchanged, while the glossary's **Finalization Gate** entry already asserted the condition and attributed it to rule 1; this closes that gap. Updated in `.github/copilot-instructions.md` (rule 1), root `CLAUDE.md` (rule 1), and `ai/templates/project-claude-template.md`, whose load-bearing rule summary carried the same unconditional wording and ships as the project's own `CLAUDE.md`. Not breaking: architectures finalized before v4.5.0, when no gate existed, remain authoritative without a gate report.
- `ai/templates/adr-template.md`: the Cross-References example link said `adr-001-modular-monolith.md` while `adr-generator` prescribes `ADR-001-<topic>.md` — the last lowercase leftover from the v4.3.0 naming alignment, and the only one in the toolkit. Corrected to `ADR-001-…`, so agents copying the template no longer emit links that 404 on case-sensitive filesystems.
- `ai/guides/quick-start.md`: removed the invented step number **Step 6.2** — the only decimal step citation in the toolkit, and not a canonical engineering-workflow step (the workflow uses 6 / 6a / 6b). It now reads "item 2 above … (engineering workflow Step 6)". The guide's own headings (Steps 1–6) are a different sequence from the canonical Steps 0b–8, so a new header note says so and points at `ai/workflows/engineering-workflow.md`; the guide already qualified canonical citations as "engineering workflow Step 6a".
- **Problem details standardized on RFC 9457** (obsoletes RFC 7807; same `application/problem+json` media type and core members, so this is a citation change only). The toolkit cited both numbers — `architecture-blueprint-template` and the gate example already said 9457 while `csharp.instructions`, `contract-definition`, `design-system-template`/`-generator`, and both backend/frontend agents said 7807. Microsoft's own docs cite both across pages, which is why the toolkit now states one. `.github/instructions/csharp.instructions.md`, root `CLAUDE.md`, and `ai/guides/contract-definition.md` carry an explicit "obsoletes RFC 7807" note; the remaining references just say 9457. Also fixes `ai/examples/contract-patterns.md`, whose GOOD contract test asserted `problem.Type == "https://tools.ietf.org/html/rfc7807"` — wrong under either RFC, since `type` identifies the problem type, not the spec, and ASP.NET Core emits an RFC 9110 status-code URI by default; it now asserts the `application/problem+json` media type, `status`, and a non-empty `title`.
- Scaffold `architecture/architecture-final-gate.md` now points at the gate prompt's `## Output` skeleton and `ai/examples/example-architecture-final-gate-report.md` for the expected shape and depth, rather than restating the format (which would duplicate the 16-check list into a second, unsynchronized place).
- New rule 18 in `.github/copilot-instructions.md` (mirrored as rule 17 in root `CLAUDE.md`): end-to-end criterion traceability.
- **MCP server aligned with the current toolkit** (closes the alignment work tracked since v4.3.0; `mcp-server/TOOLKIT-ALIGNMENT-PROMPT.md` removed). The server now knows about decomposition output — it lists `ai-parts/<slice-id>/` slice folders, reads `OVERVIEW.md` and Part files, and surfaces each Part's `Status:` line, its Part Quality Report (Step 6) and Part Code Review verdict (Step 6a, `APPROVED` / `APPROVED WITH NOTES` / `REJECTED — MUST FIX`), whether `OVERVIEW.md` carries the `## Requirement Coverage Map`, and the optional PART_SPEC fields `part_type` and `criteria_covered` (absent `criteria_covered` is reported as an unowned-criteria risk; absent `part_type` is not, since it has a defined fallback). New resources: `project://ai-parts/{sliceId}`, `project://slice-verification/{name}`, `project://architecture-final-gate`, `project://legacy-system-analysis`, `toolkit://skills/{name}`. New `get_workflow_context` steps: `golden-dataset` (Step 3b), `part-code-review` (Step 6a), `slice-preparation`, `architecture-final-gate` (between reconciliation and ADR generation), `legacy-system-analysis` (Mode D); the tool now takes an optional `sliceName`, `decomposition` serves the `plan-decomposer` skill, and `slice-verification` reports whether Step 6b evidence exists. `get_slice_context` returns both compliance reports (`<slice>.md` and `<slice>-ui.md`, now listed separately), the feature spec's criterion IDs, and the decomposition status. `.github/skills/` is served as a new `skills` category and `.json` toolkit assets are now listed and readable (`example-golden-dataset-case.json`, `golden-dataset-json-template.json`). Also fixed: with no `TOOLKIT_ROOT`/`GITHUB_ROOT` set, the server resolved its defaults one directory short and served nothing — it now walks up to the directory holding both `ai/` and `.github/`. No toolkit asset changed; this is server-side only.
- **MCP server: the UI design-system path is now served.** The alignment pass covered every workflow except UI foundation and retrofit — `ui-inventory`, `design-system-generator`, and `design-system-from-inventory` were reachable only as raw files, and the two existing UI steps (`ui-compliance`, `ui-remediation`) both served `ui-compliance-check`, so nothing assembled context for *producing* a design system. `get_workflow_context` gains three steps: **`ui-foundation`** (`design-system-generator` + `design-system-template` + architecture, ADRs, project context, and any existing design system — UI foundation workflow Step 1 / engineering workflow Step 0b), **`ui-inventory`** (`ui-inventory` + `ui-inventory-template` — UI retrofit Step 1), and **`design-system-from-inventory`** (`design-system-from-inventory` + `design-system-template` + the inventory itself — UI retrofit Step 2). New resource `project://ui-inventory`, and `list_project_artifacts` now reports `ui-inventory`. Server-side only; no toolkit asset changed and no existing step, resource, or tool signature changed.
- **MCP server path containment hardened.** `get_toolkit_file`'s `category` argument was caller-supplied but unvalidated: it was combined into the base directory before the containment check, so a rooted category (`Path.Combine` silently drops everything before a rooted segment) or a traversing one (`../../..`) became the base directory itself and the check then passed against it — letting the tool read any file the server process could reach. The category is now matched against the closed set of served categories and an unknown category returns null; the file name must be a single path segment (separators join `..` and rooted paths as rejected); and the containment check compares against the base directory with a trailing separator and an ordinal comparison, so a sibling directory sharing a name prefix no longer reads as inside it and the check no longer depends on guessing whether the filesystem folds case (`ProjectContentService.ReadSafe`'s equivalent check was tightened the same way, for one containment rule rather than two). Tests cover the three reachable guards and were mutation-checked; the containment refinements are unreachable behind those guards and ship as defense in depth, so they carry no test. Server-side only; no toolkit asset and no tool signature changed.
- **Calibrated against the reference project.** The new machinery was replayed against the reference project's slice 2.9 P12, whose round-1 review (snapshot `a0d366c`) missed defects that rounds 2 and 3 later found in that same original code. Of the seven named criteria, six are structurally caught in a single pass: preview cancellation and the clear/reset path by D3, visible labels and the pending spinner by D6, the raw instrument codes by D5 plus the evidence rules, and the unobserved history refresh by D7 **and** the mandatory cache-invalidation mutation check. The seventh (a Minor shared-component pattern deviation) remains an ordinary check-4 judgment call. Round 1 had explicitly cited 807-key English/Dutch catalogue parity as evidence that localization was complete — the exact claim round 3 demolished, and the exact claim the new evidence-rules table names as *not evidence*. Calibration feedback folded in: the reviewer must mark a dimension or coverage row `DEFERRED` with a reason when it cannot verify a claim in its own environment, rather than upgrading the executor's claim to `PASS`.
- Synced: `README.md`, root `CLAUDE.md`, `ai/CLAUDE.md` (four new cross-reference chains: criterion ID prefixes, quality report section numbers as a handoff contract, the twelve checks, examples), `ai/guides/toolkit-map.md`, `ai/guides/operating-model.md`, `ai/guides/quick-start.md`, `ai/guides/how-feature-specs-are-used.md`, `ai/guides/definition-of-ready-and-done.md`, `ai/templates/project-claude-template.md`.
